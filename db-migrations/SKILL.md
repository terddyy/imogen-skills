# DB Migrations

A migration that runs instantly on a dev DB with 50 rows can lock a 10M-row production table for minutes. Always read the SQL the tool will actually run.

## Step 0: Read the stack

1. Find the tool and its folder: `prisma/migrations/`, `drizzle/`, `migrations/` + `knexfile`, `alembic/versions/`, `<app>/migrations/`, `db/migrate/`, `src/main/resources/db/migration/` (Flyway), `changelog*.xml` (Liquibase), `*.sql` with `-- +goose`, `Migrations/` (EF Core).
2. Find the database and version (connection string, `docker-compose.yml`, infra config). Postgres and MySQL lock differently; check each operation against the right one.
3. Find how migrations run on deploy (CI step, entrypoint, release command) and whether they run before or after the new code goes live.
4. Ask the dev for rough row counts of the tables being altered, or check staging. Under ~100k rows most rules below relax; say so when they do.

## Step 1: Generate, then read the SQL

Use the repo's command, then look at the SQL:

- Prisma: `prisma migrate dev --create-only`, then read `migration.sql`.
- Alembic: `alembic revision --autogenerate`, then `alembic upgrade <prev>:<rev> --sql` (offline mode prints the SQL).
- Django: `makemigrations`, then `sqlmigrate <app> <number>`.
- Rails: run it locally and read the `db/structure.sql` or `schema.rb` diff. EF Core: `dotnet ef migrations script`.

Check autogenerated output: tools often turn a rename into drop + add, which loses data.

## Step 2: Check each operation (Postgres defaults; check MySQL online DDL separately)

- **Add nullable column**: safe.
- **Add column with a constant default**: safe on PG 11+ (no rewrite). Volatile defaults like `now()` per row still rewrite.
- **Add NOT NULL column**: add nullable, backfill, then enforce NOT NULL in a later migration.
- **Make existing column NOT NULL**: `ADD CONSTRAINT ... CHECK (col IS NOT NULL) NOT VALID`, then `VALIDATE CONSTRAINT`, then `SET NOT NULL` (PG 12+ skips the scan), then drop the check.
- **Add index**: `CREATE INDEX CONCURRENTLY`, outside a transaction (Prisma: hand-edit the SQL and put the concurrent index alone in its own migration; Alembic: `autocommit_block()`; Django: `AddIndexConcurrently` + `atomic = False`; Rails: `algorithm: :concurrently` + `disable_ddl_transaction!`).
- **Add unique constraint**: check for duplicates first, build the unique index concurrently, then attach the constraint using it.
- **Add foreign key on a big table**: add `NOT VALID`, then `VALIDATE CONSTRAINT` in a separate step.
- **Rename column or table**: never in place on a live table. Use `safe-change` (expand/contract).
- **Drop column**: remove all code usage and the ORM mapping first, deploy, then drop in a later release.
- **Change column type**: usually rewrites the table. New column, backfill, switch reads, drop old.

For risky DDL, set a lock timeout so the migration fails fast instead of queueing every query behind it: `SET lock_timeout = '5s';` (Postgres) at the top of the migration.

## Step 3: Data migrations and backfills

- Keep data changes in their own migration, never mixed with DDL.
- Don't import live app models into old migrations; use the tool's historical model (`apps.get_model`) or plain SQL.
- Batch it. One `UPDATE` over millions of rows holds locks and bloats the WAL/binlog:

```sql
UPDATE invoices SET state = status
WHERE id IN (SELECT id FROM invoices WHERE state IS NULL ORDER BY id LIMIT 1000);
-- repeat until 0 rows updated; commit between batches
```

- Backfills that take more than a few minutes belong in a script or job run after deploy, not in the migration.

## Step 4: Reversibility and history

- Every migration has a down/reverse step, or a comment saying why it's irreversible.
- Run it both ways locally: up, down, up.
- Never edit a migration that has run in any shared environment. Write a new one.
- After a merge with conflicting migrations, regenerate or merge with the tool's command and re-check ordering.

## Step 5: CI and deploy notes

- The repo's drift check passes (`prisma migrate diff`, `alembic check`, `makemigrations --check`).
- In the PR description: tables touched, row counts, expected locks, deploy order relative to code, how to roll back. `pr-description` picks this up.

## Rules

- Code must work with both the old and new schema during a deploy.
- No raw SQL step without its reverse, unless it's marked irreversible.
- Never run a migration against a shared or production database from this skill; that is the deploy pipeline's job.
