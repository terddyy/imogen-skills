# Dependency Upgrade

Upgrade in steps small enough that when something breaks, you know which step broke it.

## Step 0: Read the stack

Find the manifest and lockfile: package.json with package-lock.json / pnpm-lock.yaml / yarn.lock / bun.lockb, pyproject.toml with poetry.lock / uv.lock or requirements*.txt, go.mod/go.sum, Cargo.toml/Cargo.lock, Gemfile.lock, composer.lock. Use the package manager that matches the lockfile. Find the test, build, lint and type-check commands (README, Makefile, scripts, CI config) and the runtime version pins (`.nvmrc`, `.python-version`, `engines`, Dockerfile, CI matrix).

## Step 1: Know where you are

1. Current and target versions: `npm ls <pkg>` / `pnpm why <pkg>`, `pip show <pkg>` / `uv pip show <pkg>`, `go list -m all | grep <mod>`, `cargo tree -i <crate>`.
2. Why upgrade: CVE, needed feature, EOL, or peer requirement of something else. A CVE fix may only need a patch release, not a major.
3. Peers and plugins that must move with it (e.g. a framework plus its router, test adapter, types package, lint plugin).
4. Run the full test suite on the current version first. Note anything already failing so you don't blame the upgrade for it.

## Step 2: Read what changed

Read the changelog, release notes and migration guide for every major between current and target (GitHub releases, `CHANGELOG.md`, the docs site; use Context7 or the official docs, not memory). List each breaking change, deprecation, and new runtime or peer requirement.

## Step 3: Check breaking changes against real usage

For each breaking change, search the code:

```bash
grep -rn "from 'lib'" src/ | wc -l          # how widely it's imported
grep -rn "removedFunction\|oldOption" src/   # each removed or renamed API
```

Build a short table: change, affected files (count and examples), fix (codemod / manual / not used). Changes the repo doesn't use need no work, so say so.

## Step 4: Upgrade one major at a time

For each major version step:
1. Bump it plus its required peers: `npm install lib@4`, `pnpm up lib@4`, `uv add "lib>=4,<5"`, `go get mod@v4`, `cargo update -p crate --precise 4.x.y` (or edit Cargo.toml).
2. Run the official codemod if there is one (e.g. `npx @lib/codemod v4`), then review its diff by hand.
3. Fix the remaining breaks from your table, then deprecation warnings that will become errors in the next major.
4. Run build, type check, lint and tests. Fix before going to the next major.
5. Commit this step alone: manifest, lockfile and code changes together.

Only upgrade the packages in scope. Don't run a blanket `npm update` or regenerate the whole lockfile unless that is the task.

## Step 5: Report

```
lib 2.8 -> 4.1 (two steps)
Breaking changes hit: 3 of 11 (renamed createClient options in 6 files, dropped Node 16, new default timeout)
Codemod: @lib/codemod v3, v4 (reviewed)
Lockfile: only lib + 2 peers changed
Tests: all green; manual check of login flow on the dev server
Watch after deploy: request timeout default changed 30s -> 10s
```

## Rules

- Never skip reading the migration guide for a major version.
- The lockfile is committed with the manifest change, generated by the repo's own package manager.
- No unrelated upgrades or refactors in the same PR.
- If a runtime bump is needed (Node, Python, Go), update every pin: version files, Dockerfile, CI, `engines`.

Next: `verify-done`, then `pr-description`. For a framework jump with many breaks, `refactor-plan` to sequence the code changes.
